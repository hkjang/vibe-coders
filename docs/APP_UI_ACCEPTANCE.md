# 신규 콘솔 인수 검증표

이 문서는 사용자 요구사항의 최종 인수 기준과 필수 브라우저 시나리오를 실제 구현·검사 근거에 연결한다.
기준선은 `v0.86.4` 개발 헤드이며, 새 기능은 관련 검사를 통과한 뒤 표를 갱신한다.
기능 등록 36개, API 선언 격차 0, 전체 테스트 통과만으로 기능 동등성이나 Stable 승격을 선언하지 않는다.

## 근거 해석

- **회귀 근거 있음**: 해당 구현과 자동 검사가 있다. 특정 릴리즈의 CI 통과 여부는 그 릴리즈 커밋으로 별도 확인한다.
- **부분 검증**: 일부 구현·검사는 있으나 전체 인수 조건을 입증하지 못한다.
- **잔여 작업**: 실제 누락된 기능 또는 보호 절차를 확인했다.
- Playwright의 기존 `web/tests/e2e` 검사는 API 응답을 가로채는 UI 흐름 검사다. 별도의 Go 단위·통합 검사가
  통과하더라도 실제 브라우저부터 Go 인증·DB까지 이어진 동일 실행의 증거로 합치지 않는다.
- 기능별 운영 Preview 사용자 검증, 안정성 관측 기간·목표, 허용 복귀율과 Stable 승격은 별도 운영 의사결정이다.
  테스트 개수나 선택적 방문 집계만으로 자동 승인하지 않는다.

## 다음 구현·검증 순서

1. 미저장 변경 보호 확대: 공통 `FormDialog`는 `v0.86.4`에서 단위·브라우저 검증을 추가했다.
   콘솔 전환·SSO·알림·개별 설정 등 자체 편집창과 인라인 저장 폼을 구분해 적용한다.
   입력값·Secret을 브라우저 영속 저장소로 복구하지 않으며, 검색/필터·시뮬레이션 입력을
   모두 저장 폼으로 간주하지 않는다.
2. 실제 Go 서버를 이용한 인증·권한 브라우저 흐름: 격리 DB/로컬 IdP, 로그인·SSO·동시 갱신,
   로그아웃·다른 계정·다른 탭 캐시 격리. 운영 인증 설정이나 계정은 변경하지 않는다.
3. 공급자 삭제와 라우팅·정책 변경 검토: 비밀값·마스킹된 식별자를 보존하는 참조 영향 조회,
   대상 확인, 변경 전후 비교, 초안 변경 시 검토 무효화. 기존 서버 권한·감사는 유지한다.
4. 정책 일괄 가져오기·게이트웨이 키 회전: 일부 항목만 반영되지 않는 서버 계약과 백업·복구·다중
   pod 전환 검증을 먼저 설계한다. 개인 API Key 회전을 서버 비밀키 회전 완료로 세지 않는다.
5. 데이터 정합성·대규모 목록·실제 성능 및 운영 Preview 근거를 모은 뒤 기능별 승격을 검토한다.

이 순서는 위험을 줄이는 개발 계획이며 앞 단계 검사가 실패한 상태에서 운영 변경이나 다음 단계
Stable 승격을 진행해도 된다는 허가가 아니다. `/admin`은 계속 유지한다.
