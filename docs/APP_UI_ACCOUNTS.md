# 로그인 계정 검색과 서버 페이지

v0.86.76 후보는 로그인 계정 목록을 서버에서 검색·정렬·페이지로 나눈다. 기존 계정 등록과
역할·상태 변경, 인증, 팀 권한 검사를 사용한다. 기능은 Preview이며 운영 Stable 승격과
전체 React Phase 0–6 인수는 계속 진행한다.

## 전역 이름 검색 (v0.86.90 후보)

`Ctrl/Cmd + K` → `자원 검색`에서 로그인 계정 이름을 검색하고 등록 정보 상세를 연다.
현재 계정 목록 페이지나 필터에 없는 계정도 조회 권한 안에서 선택할 수 있다. 상세 주소는
정확한 `account_id`를 보존하며 새로고침 후에도 열리고, 닫으면 본문으로 초점을 돌린다.
조회 전용 계정도 사용할 수 있다. v0.86.90 미만의 서버에는 새 검색 종류를 보내지 않는다.

전역 검색은 이름 2–128자를 입력하고 종류별 최대 10개를 표시한다. 이메일·계정 ID·역할·
비밀번호·키·사용량은 검색하지 않는다. 검색어는 POST 본문으로 보내며 주소에 남기지 않는다.
결과는 ID와 표시 이름만 포함하고 민감정보로 보이는 값과 크기 제한을 넘는 값은 제외한다.
큰 기존 계정 정보와 더 넓은 필터는 아래 계정 목록에서 확인한다. 추가 결과 안내는 정확한
전체 건수가 아니며, 일부 종류 조회 실패가 발생하면 정상 결과를 유지하면서 다시 조회한다.

기존 로그인 계정 API의 주 소속 팀 범위를 적용한다. 팀 관리자는 같은 주 소속 팀의 계정만
검색하고, 주 소속 팀이 없으면 미소속 계정만 검색한다. 다른 팀의 계정에 보조 구성원으로
등록되어 있어도 범위를 넓히지 않는다. 계정·팀·세션·조회 권한이 바뀌면 이전 결과를 폐기한다.
변경 API와 기존 관리자 화면을 유지하며 운영 Stable 승격은 별도 검증을 거친다.

## 화면과 주소

`/app/access/users/accounts`에서 로그인 계정을 관리한다. 기존 `/app/access/users`와
`?tab=users` 주소도 검색 조건을 유지하여 이 화면으로 연결한다. 팀·API 키·할당량·역할·IP
탭과 기존 `/admin`은 계속 사용할 수 있다. 계정 화면은 다른 관리 편집기와 별도로 로딩하여
화면별 번들 크기 기준을 유지한다.

- 계정 검색: 이메일·이름·계정 ID·역할 코드·주 소속 팀 ID·팀 이름을 검색한다.
- 계정 상태: 전체·사용·중지를 선택한다. 중지는 기존 변경 API의 `disabled` 값으로 조회한다.
  역할 코드는 사용자 정의 역할도 지정할 수 있다.
- 소속 팀: 조회 가능한 전체 팀, 팀 미지정, 정확한 팀 ID를 선택한다.
- 필터 적용: 입력이 끝난 뒤 검색한다. 조건을 바꾸면 첫 페이지부터 조회한다.
- 다중 정렬: 최대 세 기준을 우선순위대로 적용한다. 기본값은 생성 시각 내림차순이며
  값이 같으면 계정 ID 오름차순으로 순서를 고정한다.
- 페이지: 10·25·50개씩 조회한다. 주소에 필터·정렬·페이지·표시 건수를 저장하므로
  새로고침과 직접 접근 시 복원한다. 범위를 벗어난 페이지에서는 마지막 페이지로 이동한다.
- 열 설정: 표시 여부·순서·너비를 조절한다. 이메일과 작업 열은 유지한다. 좁은 화면은
  표 안에서 가로로 이동한다.
- 현재 페이지 CSV: 화면에 받은 페이지의 계정 메타데이터만 내보낸다. 전체 검색 결과의
  일괄 내보내기는 아니다. 생성 시각은 ISO 8601이며 스프레드시트 수식 문자를 이스케이프한다.

검색은 최대 200개 유니코드 문자, 역할·팀 ID는 최대 256바이트다. 비밀값과 제어 문자는
검색 주소나 요청에 넣지 않는다. 필터 적용 후 입력창·버튼의 키보드 초점을 유지한다.
SQLite에서도 비ASCII 문자의 대소문자를 구분하지 않고 검색한다. 생성 시각 정렬은 같은 초
안의 소수점 이하 순서까지 반영하며 저장된 시각과 응답 메타데이터는 바꾸지 않는다.
이 제한은 새 검색 입력에 적용한다. 기존 계정·팀 메타데이터와 인증된 사용자의 팀 범위에
새 길이 제한을 적용하지 않으므로 긴 기존 팀 ID도 기본 계정 목록에서 조회할 수 있다.

## 조회 범위와 오류

로그인 계정과 프록시 키 사용량은 별도로 조회한다. 한쪽 장애가 다른 쪽 정상 데이터를
가리지 않는다. 계정 수를 확인하지 못한 상태는 0개 대신 `미확인`으로 표시한다. 일시 장애에
이전 데이터가 있으면 마지막 정상 값과 갱신 시각을 표시하고 재시도할 수 있다.

팀 관리자는 기존 관리자와 동일한 주 소속 팀의 계정만 조회한다. 팀 필터와 검색은 이 범위
안에서 적용되며 전체 건수도 같은 범위다. 주 소속 팀이 없는 팀 관리자의 기존 동작은
팀 미지정 계정 조회다. 별도의 팀을 입력해도 조회 범위를 넓히지 않는다.

계정·팀·세션·조회 권한이 바뀌면 이전 캐시와 늦은 응답을 폐기한다. 잘못된 페이지,
중복 계정 ID, 누락된 전체 건수는 정상 목록으로 표시하지 않는다. 읽기 전용 상태에서는
기존 변경 권한 보호가 적용된다. SSO 등 외부에서 만든 계정의 기존 편집 제한도 유지한다.

## API 호환성

기존 `GET /admin/users`에 선택적인 조회 방식을 추가한다. 기존 변경 API와 업무 로직을
복제하지 않는다.

| 호출 | 응답 |
| --- | --- |
| 조회 방식 생략 | 기존 `users`, `auth_users`, `team_names` |
| `view=usage` | 기존 키 사용량 `users`, `team_names`만 조회 |
| `view=accounts` | `accounts`, `total`, `limit`, `offset` |

계정 조회는 `q`, `role`, `status`, `team_id`, `sort`, `limit`, `offset`을 사용한다.
`team_id` 생략은 추가 팀 필터 없음, 명시적인 빈 값은 팀 미지정이다. 정렬은
`field:asc,field:desc` 형식이며 허용 필드 최대 세 개와 계정 ID 보조 순서를 사용한다.
API의 limit은 1–100, offset은 0–1,000,000이다. 중복된 알려진 계정 조회 매개변수,
잘못된 인코딩·필터·정렬은 400으로 거부한다. 정상·실패 GET 응답은 캐시하지 않는다.

팀 범위·검색·건수·페이지는 한 SQL 문에서 계산한다. 비밀번호 해시는 조회하지 않으며
공개 계정 메타데이터만 응답한다. 기존 사용자 조회의 계정별 팀 조회를 새 페이지에서는
수행하지 않는다. OpenAPI에 세 응답을 명시하고 실제 Go 서버 문서에서 타입을 생성한다.

프록시 키 사용량·AI 활용지수의 기존 집계 범위는 바꾸지 않는다. 서버 페이지 방식은
이번 단계의 로그인 계정 목록에 적용된다.

## 검증

SQLite와 PostgreSQL의 실제 저장소·HTTP 테스트에서 팀 범위, 빈 팀, 전체 건수,
페이지 경계, 같은 시각의 순서, 문자 그대로의 검색, 다중 정렬, 취소, 잘못된 입력,
비밀번호 해시 제외와 기존 응답 일치를 검사한다. 두 저장소의 레이스 검사도 수행한다.

React 테스트는 주소 복원, 필터 적용, 페이지 크기, 오류 재시도, 응답 계약과 기존 계정
편집·권한 회수·계정 교체를 확인한다. 실제 브라우저에서 네 화면 크기와 밝은·어두운 테마의
키보드·axe 검사, 초점 유지, CSV와 새로고침을 검증하고 데스크톱·모바일 시각 기준을 유지한다.
CI의 기존 관리자·인증·Go·컨테이너·공급망 검증은 계속 수행한다.
