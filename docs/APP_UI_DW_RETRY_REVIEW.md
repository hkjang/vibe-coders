# DW 재처리 검토와 작업 상태

신규 콘솔의 **데이터 분석 → 데이터 웨어하우스 → 적재 상태**에서 실패분을 다시 보낼 때 대상 기간과 예상 건수를 먼저 확인합니다. `실패분 재처리`를 누르면 검토 화면이 열리며, 실행 사유를 입력한 뒤 명시적으로 실행합니다. 검토만으로 ClickHouse에 데이터를 보내거나 실행 감사 기록을 남기지 않습니다.

## 사용 흐름

- 차원별 시작·종료 범위, 예상 건수, 실행 가능 여부를 확인합니다. 연결되지 않은 팩트 테이블 등은 실행 불가 이유를 표시합니다.
- 검토는 5분 동안 유효합니다. 대기열·연결 설정·예상 건수가 바뀌면 새로 검토해야 합니다. 이전 사유를 유지하되 다시 확인한 결과로 실행합니다.
- 실행 중에는 같은 검토의 중복 실행을 막고 작업 상태를 조회합니다. 주소의 `retry_job`에는 비밀정보 없이 작업 식별자만 저장되어 새로고침 후에도 이어서 볼 수 있습니다.
- 실행 응답을 놓쳤다면 `접수 결과 확인`으로 작업을 조회합니다. 자동 재전송하지 않습니다. 같은 검토를 다시 제출하더라도 기존 작업을 반환합니다.
- 완료 건수는 전송기가 수락을 확인한 행 수입니다. 일부 실패와 새 실패가 남은 경우 이를 완료와 구분하며, 재처리는 대기열을 새로 검토한 뒤 실행합니다.
- 작업자의 상태 갱신이 끊기면 중단 상태로 표시합니다. 마지막으로 확인된 진행량을 유지하며 해당 작업을 자동 재개하지 않습니다.

읽기 전용 계정에는 실행 버튼을 비활성화합니다. 조회 API는 기존 읽기 권한으로 대상을 검토할 수 있지만 실행은 쓰기 권한이 필요합니다. 작업 결과는 해당 작업을 시작한 계정만 조회합니다. 화면에서 버튼을 숨기는 것에 그치지 않고 기존 관리 API가 권한을 다시 검사합니다. 실행 중 권한·계정이 바뀌면 이전 화면의 응답을 폐기합니다.

## 데이터와 감사

기존 `/admin/dw/sink-retry`에 조회와 검토 후 실행 방식을 추가합니다. 기존 관리자 화면의 POST 방식은 유지합니다. 별도 DW 전송 로직을 만들지 않고 정기 적재와 수동 재처리가 동일한 전송기를 사용합니다.

텍스트 SQL·레드팀 팩트는 해당 전송기로 보내며 일별 집계와 구분합니다. 전송 구간의 상한을 고정하고 시간·식별자로 최대 1,000행씩 읽습니다. 같은 시각의 데이터나 5,000행을 넘는 집계도 끝까지 처리합니다. 예상 건수와 전송 대상은 같은 조건으로 조회하며 과거 실패의 가장 이른 경계를 유지합니다. 전송 중 새 실패가 기록되면 기존 시도의 완료 처리로 새 실패를 삭제하지 않습니다.

작업 접수·완료 상태와 해당 감사 기록은 각각 같은 DB 트랜잭션에 저장합니다. 여러 서버에서 동일 검토의 접수와 실행 중인 다른 검토의 충돌을 검사합니다. 실제 전송 중 DB 트랜잭션을 열어 두지 않습니다. 작업 진행은 DB에 남아 다른 서버에서도 조회할 수 있으며 작업자 식별자·연결 비밀번호·내부 상태 기한은 API 응답에 포함하지 않습니다.

예상 건수는 검토 시점의 대상 범위입니다. 이후 원본 집계가 갱신될 수 있으며, ClickHouse가 수락한 직후 통신이나 DB 기록이 실패하면 전달 여부를 확정하지 못할 수 있습니다. 이 경우 성공으로 추정하거나 자동 재전송하지 않습니다. 외부 저장소까지 정확히 한 번 전달됨을 보장하는 기능은 아닙니다. 새 검토를 통한 재처리는 기존 ClickHouse 테이블의 중복 처리 정책을 따릅니다.

## 검증 범위

실제 기존 경로에서 잘못된 팩트 전송, 5,000행 이후 누락, 전송 중 새 실패 삭제를 수정 전 실패로 재현했습니다. SQLite·PostgreSQL의 범위·동일 시각 페이지·동시 접수·작업자 소유권·감사 트랜잭션 실패·중단 작업 복구를 검사합니다. 8,000행의 이전 이력 사이에서 5행을 조회하는 자연 실행 계획을 두 DB에서 확인하며 인덱스를 강제로 선택하지 않습니다.

React 검사는 검토·사유·오래된 검토·부분 실패·응답 유실·권한 회수·미저장 변경을 다룹니다. 생산 브라우저 검사는 390px·1440px의 밝은/어두운 화면, 표의 열 경계, 접근성, Escape와 초점 복귀를 포함합니다. 검토 대화상자를 닫는 과정에서 미저장 변경 보호가 작업 주소 반영을 막던 문제를 재현하고, 접수 후 보호 상태가 해제된 뒤 주소를 반영하도록 수정했습니다.

별도 실제 Go 브라우저 검사는 정상 인증을 거쳐 작업을 접수한 뒤 응답만 유실시킵니다. 브라우저의 조회 복구·새로고침·동일 검토 재접수와 수신기의 실제 전송 1회·1행, 영속 작업 결과·사유·실행자·감사 기록을 대조합니다. 읽기 전용 실행 및 타 계정 작업 조회 거부도 확인합니다. 외부 네트워크 없이 로컬 수신기를 사용하며 인증 정보가 담긴 화면·추적·원문 로그는 보관하지 않습니다.

## 후보 리뷰 후 보완

자동 팩트 적재에서 마지막 전송 시각을 포함해 매 주기 같은 데이터가 다시 전송되던 문제를 실제 수신기에서 재현했습니다. 정상 증분 적재는 DB에 저장한 시각·식별자의 다음 행부터 읽습니다. 이전 버전의 시각 전용 기록은 기존의 엄격한 시작 경계를 유지하며, 전송할 새 행이 없으면 확인된 기록을 바꾸지 않습니다. 대기 중인 실패나 명시적 재처리는 기존처럼 선택한 시작 경계를 포함합니다. 원본 시각보다 뒤늦게 들어오는 과거 데이터는 해당 범위를 명시적으로 재처리해야 합니다.

처리 이력 8,000행 뒤의 마지막 5행을 조회하는 실제 SQL에서 8,005행을 검사하던 경로도 재현했습니다. 시각·식별자를 한 번에 비교하여 다음 위치를 찾도록 변경하고 첫 페이지·뒤쪽 페이지에 사용되는 실제 전송 쿼리의 자연 실행 계획과 결과를 검사합니다.

재처리 후 같은 화면에서 새 실패분 검토를 열면 입력 잠금이 남는 문제를 재현하고 보완했습니다. 이전 접수가 확인된 경우 명시적으로 다시 여는 검토는 새 사유를 입력할 수 있습니다. 접수 여부가 불확실한 경우에는 창을 닫았다 열어도 재전송 잠금을 유지하며 조회 복구·명시적 재검토 흐름을 따릅니다.
