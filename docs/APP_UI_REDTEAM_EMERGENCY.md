# 레드팀 긴급 제어

`/app/redteam`에서 응답 서버의 레드팀 실행 중지 상태를 확인하고 변경을 검토한다. v0.86.136부터 기존 `/admin/redteam/kill-switch` API에 상태 검토와 감사 확인을 추가한다. 기능은 Preview로 유지한다.

## 화면 사용

1. **레드팀 긴급 제어**에서 상태·응답 서버 식별자·확인 시각을 읽는다. 조회 실패는 “현재 상태 미확인” 또는 “마지막 확인”으로 구분한다. 성공적으로 읽은 최신 상태에서만 변경할 수 있다.
2. **레드팀 처리 중지 검토** 또는 **레드팀 처리 재개 검토**를 누른다. 영향 범위와 검토 대상 서버를 확인한다.
3. 확인 문구를 그대로 입력하고 1,000자 이내의 변경 사유를 작성한다. 중지와 해제 모두 같은 절차를 거친다.
4. 처리 결과가 불명확하면 같은 확인 창에서 다시 보내지 않는다. **현재 상태만 다시 조회**로 상태를 확인하고 창을 취소한 뒤 새로 검토한다.

다른 레드팀 조회가 실패해도 긴급 제어 조회는 독립적으로 제공한다. 기존 서버가 검토 정보를 제공하지 않으면 상태만 보여 주고 신규 화면의 변경을 잠근다. 조회·쓰기 권한 및 기능별 읽기 전용 설정을 적용하며, 계정·팀·세션 또는 권한 변경 시 이전 확인을 재사용하지 않는다. 갱신·쿼리 취소·교체 후에도 검토를 다시 해야 한다.

## 적용 범위와 감사

제어 범위는 **응답한 서버 프로세스**다. 새 캠페인, 예약/변경 후 실행의 시작과 다음 테스트 진입에서 기존 실행기가 상태를 확인한다. 이미 외부로 전송한 모델 호출을 취소하지 않으며 다른 서버의 상태도 변경하지 않는다. 재시작하면 중지 상태가 초기화된다. 해제해도 중단된 실행이 자동으로 이어지지는 않는다.

서버는 조회 당시의 임의 검토 토큰을 변경 요청에서 다시 확인한다. 정상적으로 수락한 기존·신규 요청마다 토큰을 교체하므로 같은 값으로의 변경이나 중지→해제 뒤에도 과거 검토를 적용할 수 없다. 다른 프로세스에서 확인한 토큰과 동시에 재사용한 토큰은 충돌로 거부한다. 같은 프로세스 안의 Server 객체들은 기존 실행기의 전역 플래그와 검토 수명을 공유한다.

사용자·시각·사유·전후 상태·익명 프로세스 식별자를 기존 관리자 감사 저장소에 먼저 기록한다. 감사 저장 확인에 실패하면 플래그를 바꾸지 않는다. 감사 기록과 메모리 플래그는 영구 저장되는 단일 트랜잭션이 아니다. 둘 사이의 프로세스 종료나 DB 응답 유실은 감사만 남길 수 있으므로 결과가 불명확할 때 자동 재전송하지 않는다. 검토 토큰과 원래 서버 식별자는 감사에 저장하지 않는다.

`/admin` 화면과 정상적인 기존 `{ "enabled": true/false }` 요청은 유지한다. 생략/null 플래그는 기존처럼 false이며 검토 토큰이 없는 요청은 기존 방식으로 처리한다. 잘못된 JSON·잘못된 타입·복수 JSON·크기 초과 본문은 변경 없이 거부한다. 신규 화면은 항상 명시 상태·사유·검토 토큰을 보낸다. 응답은 `no-store`이며 확인 사유는 변경 응답에만 포함한다.

## 검증

변경 사유의 1,000자 제한은 UTF-16 단위가 아닌 유니코드 코드 포인트 기준이다. 고정한 Zod 4.6.6도 같은 기준을 사용한다. 실제 API 클라이언트의 응답 검증과 확인 창 성공 처리를 거치는 회귀 검사를 추가해 ASCII·한글·이모지·보충 한자·결합 문자의 경계를 확인했다. 관련 집중 검사 43개와 SQLite·PostgreSQL 17의 경계 초과 거부·감사 수 보존 race 검사를 통과했다. 이 보강은 테스트와 문서에 한정하며 실행 코드를 변경하지 않는다.

관련 React 1,100개(50개 파일), 최종 내장 브라우저 64개, 두 테마·1440/390px 시각 기준 8장과 키보드·axe·반응형 검사를 통과했다. Go proxy/appui 전체 회귀·vet, SQLite와 PostgreSQL 17의 검토·동시 요청·감사·JWT 권한 race, API 표면·실제 Go OpenAPI·생성 타입·린트·포맷·빌드·SBOM을 확인했다. 초기 압축 번들은 264,728바이트다. 실제 Go/OIDC/SQLite 인증 60개·Keycloak HTTPS 5개와 사용자 DB·보고서 29개는 초기 구현 빌드에서 통과했다. 이후 변경은 레드팀 화면의 배치·한글 라벨·사유 길이 안내와 관련 검사 5개 파일로 제한했고, 백엔드·인증 소스 불변을 해시로 확인했다. 최종 화면은 새 내장 자산으로 다시 검증했다. 운영 중 실제 레드팀 호출이나 실제 비밀키를 사용하지 않는다. 다중 서버 일괄 중지·실행 중인 외부 호출 취소·상태 영구 보존 및 운영 Stable 인수는 별도 범위다.
