# 레드팀 실행 작업과 상태 복구

신규 콘솔의 **보안 → 레드팀 자동화 → 캠페인**에서 검토한 실행을 접수하면 서버가 작업을 처리하고 화면에는 진행 상태가 표시됩니다. 검토와 사유 입력, 캠페인 이름 재확인, 실제 모델 호출의 실행 키·비용·토큰·호출 수 제한은 기존 실행 절차를 그대로 따릅니다.

## 사용 흐름

- 검토한 조건으로 한 번 실행하면 검사 완료 건수, 실제 모델 호출 수, 기록된 비용, 마지막 확인 시각을 표시합니다. 넓은 화면은 네 항목을 한 줄에, 좁은 화면은 두 항목씩 정렬합니다.
- 작업 접수가 끝나면 창을 닫거나 새로고침해도 서버의 처리는 계속됩니다. 주소의 `execution_job`과 `job_campaign`으로 같은 작업을 다시 조회합니다. 주소에는 실행 키나 검토 토큰을 넣지 않습니다.
- 실행 응답을 놓쳐도 자동으로 재실행하지 않습니다. 접수 전 조회가 먼저 도착할 수 있어 처음 30초 동안은 작업의 존재 여부를 다시 확인하며, 이후에는 사용자가 `작업 상태 새로고침`으로 확인할 수 있습니다.
- 진행 중에는 활성 화면에서 2초 간격으로 조회합니다. 완료·중단·오류가 확인되면 자동 조회를 멈춥니다. 완료 후 `저장된 실행 결과`로 기존 결과 화면을 엽니다.
- 작업 표시를 닫는 것은 서버 실행 취소가 아닙니다. 실행 제한이나 긴급 중지는 기존 실행기의 검사를 따릅니다.

작업은 접수한 계정만 조회합니다. 읽기 권한이 있더라도 다른 계정의 작업 주소는 열 수 없습니다. 계정·세션·권한이 바뀌면 이전 작업 캐시와 뒤늦은 응답을 화면에 사용하지 않습니다. 모델 실행 키는 해당 실행 중 메모리에서만 사용하며 작업·주소·브라우저 저장소·감사 기록에 남기지 않습니다.

## 중단과 불확실한 결과

서버의 작업 상태 갱신이 끊기면 마지막으로 확인된 진행량과 함께 연결 끊김을 표시합니다. 서버가 다시 시작되어도 저장된 상태는 조회할 수 있지만, 이전 작업을 자동으로 재개하거나 모델을 다시 호출하지 않습니다. 이력과 저장 상태를 확인한 뒤 필요하면 새로 검토해야 합니다.

실제 모델 호출 뒤 결과 저장에 실패한 경우에는 호출 수를 유지하고 결과 저장 확인이 필요한 상태로 표시합니다. 모델이 요청을 받은 직후 연결이 끊기면 외부 처리 여부를 확정할 수 없습니다. 성공으로 추정하거나 외부 제공자까지 정확히 한 번 실행됨을 보장하지 않습니다.

## 서버와 호환성

기존 `POST /admin/redteam/campaigns/{id}/run-reviewed`에 `job=1` 방식과 같은 경로의 `GET ?job_id=...` 조회를 추가합니다. 접수는 202, 같은 검토로 이미 접수된 작업은 200으로 반환합니다. 별도 실행기를 만들지 않고 기존 검토·실행·비용 제한·결과 기록 코드를 재사용합니다.

작업 접수와 감사 기록, 작업 완료와 감사 기록을 각각 같은 DB 트랜잭션에 저장합니다. SQLite와 PostgreSQL에서 여러 서버의 동일 캠페인 작업 접수를 조정하며, 같은 작업 식별자로 다시 요청해도 기존 작업만 반환합니다. 작업자 소유권과 유효한 상태 기한을 확인한 후 진행량을 갱신합니다. 작업이 진행되는 동안 모델 호출 전체를 DB 트랜잭션 안에 넣지 않습니다.

기존 `/admin`의 동기 실행, 예약 실행, 결과 한 건 재실행은 유지합니다. 이 경로들까지 작업 접수 방식으로 바뀌는 것은 아닙니다. 아직 접수되지 않은 검토는 기존처럼 검토를 만든 서버에 속합니다. 작업 식별자를 제공하지 않는 이전 서버에서는 기존 검토 실행 흐름을 사용합니다.

## 검증

SQLite·PostgreSQL의 동시 접수, 다른 서버에서 조회, 동일 작업 재접수, 작업자 소유권, 상태 기한 만료, 감사 트랜잭션 실패와 실제 호출 후 결과 기록 실패를 검사했습니다. 브라우저가 접수 요청을 취소한 뒤에도 실행이 끝나고 조회되는 경로를 검증했습니다.

실제 Go 인증과 로컬 모델 수신기를 사용하는 브라우저 검사는 접수 응답 유실, 새로고침 조회, 같은 검토 재접수, 다른 계정의 조회 거부, 모델 실제 호출 횟수와 감사 기록을 대조합니다. 외부 모델이나 유료 API는 호출하지 않습니다. 합성 데이터 브라우저 검사는 밝은/어두운 화면의 390px·1440px 배치, 키보드·접근성, 권한 회수와 기존 검토·결과·재실행 흐름을 포함합니다. 최종 브라우저 검사는 재시도나 시각 기준 갱신 없이 완료합니다.

검토 창을 열 때만 편집 모듈을 불러옵니다. 기존 화면별 번들 한도는 유지하고, 해당 선택 모듈과 필요한 의존성 전체에 별도 크기 제한을 적용합니다. API 계약·정적 분석·전체 회귀 검사와 실제 Go 내장 배포 검증을 후보 및 릴리스 단계에서 수행합니다.
