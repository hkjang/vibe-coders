# 레드팀 실행 결과의 저장 확인

v0.86.140 후보는 `/app/redteam`의 검토 실행에서 검사 수행과 데이터베이스 저장 확인을 구분한다. 기존 실행기와 저장 SQL을 재사용하며 `/admin`의 기존 화면과 예약 실행을 유지한다.

## 화면에서 확인할 내용

- **확인됨**: 검사 결과 묶음과 최종 실행·캠페인 상태의 저장 응답을 확인했다.
- **확인 실패**: 실행 기록 생성, 검사 결과 묶음 저장 또는 최종 상태 갱신 중 저장을 확인하지 못했다. 화면은 완료 대신 **저장 확인 필요**로 표시한다.
- **확인 정보 없음**: 이전 API 응답에 저장 확인 정보가 없다. 반환된 수치를 저장 성공으로 해석하지 않는다.

저장이 확인되지 않아도 이미 호출한 모델의 비용이 발생했거나 일부 기록이 남아 있을 수 있다. 같은 검토를 자동으로 다시 실행하지 않으며, 반환된 실행 식별자로 이력을 확인한 뒤 새로 검토한다. 서버의 SQL 오류 원문은 표시하지 않는다.

## 기록 계약

`POST /admin/redteam/campaigns/{id}/run-reviewed` 응답에 다음 정보를 추가한다.

| 필드 | 의미 |
| --- | --- |
| `recording.confirmed` | 이번 응답에서 결과 묶음과 최종 상태 저장을 확인했는지 여부 |
| `recording.stage` | 첫 실패 지점: `run_start`, `case_result`, `finalize`; 확인된 경우 빈 문자열 |
| `recording.results` | 저장 응답이 확인된 검사 결과 수 |
| `complete` | 계획한 검사의 수행과 결과 저장 확인이 모두 끝났는지 여부 |

검토 실행의 타입 계약은 저장 정보 누락, 확인 여부와 실패 지점의 모순, 결과 수 불일치, 저장 미확인 상태의 완료 응답을 거부한다. 이전 서버의 응답을 임의로 저장 성공으로 보정하지 않는다. 실제 모델 호출 시도와 비용은 저장된 결과 수와 별도로 표시한다.

## 서버 동작

1. 대상별 실행 기록을 먼저 생성한다. 생성 실패 시 해당 대상의 모델을 호출하지 않는다.
2. 검사 결과·증적·필요한 조치 항목을 하나의 트랜잭션으로 저장한다. 유효한 실행 기록과 각 SQL의 반영 행 수를 확인하며, 묶음 일부가 실패하면 함께 롤백한다.
3. 저장 오류가 발생하면 다음 모델·검사·대상의 호출을 중단한다. 이미 수행한 호출을 저장 실패 때문에 다시 보내지 않는다.
4. 대상별 실행 요약, 캠페인 상태와 통과 기준선을 함께 확정한다. 실행이나 캠페인 행이 없거나 갱신·기준선 저장이 실패하면 최종 갱신을 롤백하고 저장 미확인을 반환한다.
5. 중단되거나 저장 미확인인 실행은 통과 기준선을 갱신하지 않는다. 실제 적용한 검사가 없는 팩도 통과 기준선을 만들지 않는다.

호출 취소 후에는 기존과 같이 요청 취소에서 분리한 정리 시간을 사용한다. 각 결과 묶음과 최종 갱신에 각각 최대 5초를 부여한다. 네트워크·모델 호출은 DB 트랜잭션 밖에서 실행한다. 기존 저장 메서드와 트랜잭션 메서드는 동일 SQL 구현을 사용한다.

## 적용 한계

저장 확인은 데이터베이스의 커밋 응답 기준이다. 전체 캠페인과 모델 호출을 하나로 되돌리는 트랜잭션, 모델 호출의 정확히 한 번 실행, 중단된 프로세스의 자동 복구나 여러 서버의 전역 작업 잠금을 뜻하지 않는다. 확인된 개별 검사 결과는 최종 상태 갱신이 실패해도 남을 수 있고, 커밋 응답을 잃으면 실제 저장 여부가 불확실할 수 있다. 다른 관리자의 이후 기록 변경·삭제를 잠그지 않는다.

검토 토큰은 여전히 응답한 서버에서만 한 번 소비한다. 전역 실행 식별·복구, 운영 Preview 검증과 Stable 승격은 후속 인수 항목이다. 기존 `/run`·예약 실행의 결과 저장 방식을 이 후보에서 전체 전환하지 않는다.

## 검증 결과

SQLite 및 PostgreSQL 17에서 실제 로컬 HTTP 제공자와 DB 오류 주입으로 결과 묶음의 원자성, 행 누락, 반영 행 수 0, 기록 실패 후 추가 호출 중단, 기준선 롤백과 재전송 차단을 검증했다. 실행 기록 삽입이 오류 없이 무시되는 경우에도 실제 호출은 시작하지 않는다. 관련 React 1,161개(55개 파일), 최종 내장 브라우저 94개, 두 테마·1440/390px 시각 기준 8장과 키보드·axe·반응형 검사를 통과했다. 최종 내장 자산에서 실제 Go/OIDC/SQLite 인증 60개, Keycloak HTTPS 5개와 사용자 DB, 보고서·실패 산출물 29개를 검증했다. Go store/proxy/appui 전체 회귀·vet, SQLite·PostgreSQL 17 race와 DB 오류 주입, 실제 Go OpenAPI·생성 타입·API 표면·린트·포맷·빌드·통합 SBOM을 검증했다. 초기 전송 번들은 265,400바이트다. 내장 브라우저의 업무 응답은 공개 합성 fixture이며, 실제 외부 모델 서비스의 운영 검증과 구분한다. 후보 CI·리뷰·메인·공개 출고 검증과 운영 Preview·Stable 인수는 별도다.
