# 등록 팀 검색과 서버 페이지

v0.86.77 후보는 `/app/access/users?tab=teams`의 등록 팀 목록에 서버 검색·정렬·페이지를
추가한다. 기존 팀 생성과 이름 수정, 팀 관리자 범위, `/admin`을 유지한다. 기능은 Preview이며
전체 Phase 0–6 인수와 운영 Stable 승격은 계속 진행한다.

## 화면 사용

- 팀 이름이나 팀 ID를 입력한 뒤 `필터 적용`을 선택한다. 입력 중에는 요청하지 않으며,
  검색을 바꾸면 첫 페이지부터 조회한다. `%`, `_`, `!`는 문자 그대로 검색한다.
- `다중 정렬`에서 최대 세 기준을 선택한다. 이름·ID·생성 시각·수정 시각을 지원한다.
  기본값은 이름 오름차순이며 같은 값은 ID 오름차순으로 순서를 고정한다.
- 10·25·50개 페이지를 선택한다. 검색·정렬·페이지·표시 건수는 주소에 저장되며 직접 접근과
  새로고침 후에도 유지된다. 범위를 벗어난 주소에서는 마지막 페이지로 이동할 수 있다.
- 열 표시·순서·너비를 조절할 수 있다. 팀 이름과 작업 열은 유지한다. 좁은 화면에서는
  표 영역 안에서 가로로 이동한다.
- `현재 페이지 CSV`는 받은 페이지의 ID·이름·생성 및 수정 시각만 내보낸다.
  시각은 ISO 8601이며 스프레드시트 수식 문자를 이스케이프하고 보호 대상 식별자를 가린다.

검색은 최대 200개 유니코드 문자다. 비밀값이나 제어 문자는 주소·요청에 넣지 않으며
필드 가까이에 오류를 표시하고 입력창으로 초점을 돌린다. 새 검색 입력 제한을 기존 팀 ID나
이름, 인증된 사용자의 팀 범위에 적용하지 않는다.
SQLite에서도 비ASCII 문자의 대소문자를 구분하지 않고 검색한다. 생성·수정 시각은 같은 초
안의 소수점 이하 순서까지 정렬하며 기존 저장값과 응답 메타데이터는 유지한다.

## 권한과 오류

등록 팀 목록과 사용량 집계는 따로 조회한다. 한쪽 조회 실패가 다른 정상 영역을 가리지 않는다.
확인되지 않은 건수와 사용량은 0 대신 `미확인`으로 표시한다. 마지막 정상 값이 있으면
갱신 시각과 오류를 함께 제공하고 해당 조회를 재시도할 수 있다.

팀 관리자는 기존 관리자와 동일하게 주 소속 팀만 조회·수정한다. 주 소속 팀이 없으면
등록 팀 목록도 비어 있다. 검색·건수·페이지는 이 범위 안에서 계산한다.
계정·팀·세션·조회 권한이 바뀌면 이전 목록과 초안을 폐기하고 늦은 응답을 사용하지 않는다.
읽기 전용 전환은 기존 초안을 보존하되 저장을 막는다.

팀 변경은 기존 API를 재사용한다. 현재 페이지만으로 중복 ID나 이전 초안을 검증하지 않는다.
저장 직전에 기존 전체 등록 목록을 다시 조회하여 페이지 밖의 ID 충돌과 이름 변경을 확인한다.
이 조회에도 같은 권한·세션 수명을 적용한다. 401·403이면 보관된 목록과 초안을 닫는다.
이 사전 검사는 기존 동작을 유지하며 서버의 원자적 비교·저장이나 탭 간 멱등성을 뜻하지 않는다.

## API 계약

| 호출 | 응답 |
| --- | --- |
| `GET /admin/teams` | 기존 `teams`, `auth_teams` |
| `GET /admin/teams?view=usage` | 기존 사용량 집계 `teams` |
| `GET /admin/teams?view=registered` | `auth_teams`, `total`, `limit`, `offset` |

등록 팀 조회는 `q`, `sort`, `limit`, `offset`을 지원한다. 정렬 형식은
`name:asc,created_at:desc`이며 허용 필드 최대 세 개만 사용한다. API limit은 1–100,
offset은 0–1,000,000이다. 중복된 알려진 조회 매개변수, 잘못된 인코딩·범위·정렬은
400으로 거부한다. 정상·오류 GET 응답은 캐시하지 않는다.

하나의 SQL 문에서 권한 범위·검색·전체 건수·페이지를 계산한다. 스키마와 기존 변경 API는
바꾸지 않는다. OpenAPI에 세 응답을 명시하고 실제 Go 서버 문서에서 타입을 생성한다.
팀 사용량·스코어카드·벤치마크의 기존 집계 범위는 유지한다.

## 검증 범위

SQLite와 PostgreSQL에서 실제 저장소·HTTP·JWT·기존 토큰·팀 범위·긴 기존 ID·데이터 일치를
검증한다. UI 검사는 주소 복원·부분 실패·잘못된 응답·권한 회수·중복 ID·기존 이름 수정을
포함한다. 브라우저에서 CSV·키보드·초점·접근성·밝은/어두운 테마·모바일 시각 기준을 검증한다.
