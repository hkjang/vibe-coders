# 업무 활용 분석 가이드

AI가 **어떤 업무에** 쓰이는지를 업무 유형·조직·모델별로 보여 주는 기능입니다. 요청 수와 비용만으로는 답할 수 없던 질문 — 어떤 업무에 가장 많이 쓰는가, 어느 조직이 어떤 업무에 쓰는가, 무엇이 늘고 있는가, 반복되는 업무 중 자동화할 만한 것은 무엇인가 — 에 답합니다.

- 화면: 콘솔 **업무 활용 분석 → 업무 활용 분석**(`/app/insights/usage`), **업무 활용 분석 → 업무 분류 관리**(`/app/insights/classification`)
- API: `/admin/work-intel/*` (관리자 인증). 전체 명세는 `/admin/openapi.json`
- 설계와 데이터 모델: [WORK_INTELLIGENCE_DESIGN.md](WORK_INTELLIGENCE_DESIGN.md)

이 문서는 운영자(켜고 끄기, 설정, 점검, 문제 해결)와 사용자(화면 읽는 법, 분류 관리) 양쪽을 다룹니다.

---

## 1. 동작 원리 한눈에

```
요청 → 프록시 처리 → 응답            (기존과 동일. 분류 코드가 실행되지 않습니다)
          └ 요청 로그 저장 (기존 비동기 기록)
                 ↓  뒤따라가며 읽음 (기본 15초마다, 한 번에 200건)
          분류 워커: 규칙 → 캐시 → (선택) 분류 모델
                 ↓  한 트랜잭션
          요청별 분류 결과 + 세션 + 일별 집계
                 ↓
          분석 API · 화면 (집계만 읽음)
```

- **요청 처리 경로에는 아무것도 추가되지 않습니다.** 분류는 이미 저장된 요청 로그를 워커가 뒤따라가며 수행합니다. 워커를 꺼도, 워커가 실패해도 프록시 응답과 스트리밍은 영향을 받지 않습니다.
- 분석 화면은 요청 로그 원본을 훑지 않고 **일별 집계**만 읽습니다. 그래서 요청이 많아져도 화면 응답 시간이 요청 수에 비례해 늘지 않습니다.
- 분류 워커와 분석 화면은 **따로 켜고 끌 수 있습니다**(3절).
- 여러 인스턴스가 같은 DB를 쓰면 한 인스턴스만 임대(lease)를 잡고 분류합니다. 같은 요청이 두 번 집계되지 않습니다.

### 분류 순서

1. **규칙**: API 종류, 클라이언트, 호출한 MCP 도구 이름, 프로그래밍 언어, 가린 프롬프트의 핵심어를 근거로 점수를 냅니다. 단어 하나만 일치해서는 확정하지 않으며, 근거가 부족하면 `미분류`로 남깁니다.
2. **캐시**: 같은 정책 버전에서 같은 내용(프롬프트 지문)이 이미 분류됐으면 그 결과를 씁니다. 캐시는 팀과 정책 버전으로 구분됩니다.
3. **분류 모델(선택, 기본 꺼짐)**: 규칙과 캐시로 확정하지 못한 요청만 별도로 지정한 작은 모델에 묻습니다. 결과는 JSON 스키마로 검증하고, 등록된 카테고리 ID가 아니면 버립니다.

분류 결과에는 대·중·소분류, 행위 유형(조회·분석·생성·수정·삭제·검증·계획·자동화), 신뢰도, 분류 방식(규칙·캐시·모델·수동), 적용한 정책 버전이 함께 남습니다.

## 2. 처음 켜기

v0.86.186 이상으로 올리면 기본으로 **규칙 분류와 분석 화면이 켜진 상태**입니다. 따로 할 일은 없습니다.

1. 업그레이드하고 기동합니다. DB 변경(테이블 14개 추가)은 기동 시 자동으로 적용됩니다. 기존 테이블은 바뀌지 않습니다.
2. 콘솔 **업무 분류 관리 → 상태** 탭에서 워커가 돌고 있는지 확인합니다. `미처리` 건수가 줄어들고 `마지막 실행` 시각이 갱신되면 정상입니다.
3. 처음에는 최근 7일(`WORK_INTEL_BACKFILL_DAYS`) 치 요청부터 분류합니다. 요청이 많으면 화면이 채워지는 데 시간이 걸립니다(처리량은 8절).
4. **업무 활용 분석 → 요약** 탭에서 결과를 봅니다.

> 가린 프롬프트 텍스트가 저장되지 않는 환경(프롬프트 로그 보존 0일 등)에서는 프롬프트 내용 없이 메타데이터(API 종류, 클라이언트, 도구, 언어)만으로 분류합니다. 이때는 미분류 비율이 높아집니다.

## 3. 설정

콘솔 **시스템 설정**의 `업무 활용 분석` 분류에서 바꿉니다. 저장하면 재시작 없이 다음 설정 재적용 주기에 반영됩니다. 같은 이름의 환경 변수는 관리자가 값을 바꾸기 전까지의 기본값입니다.

| 설정 키 | 환경 변수 | 기본 | 설명 |
|---|---|---|---|
| `work_intel.classify_enabled` | `WORK_INTEL_CLASSIFY_ENABLED` | `true` | 분류 워커. 끄면 새 요청이 미처리로 쌓였다가 다시 켤 때 이어서 처리됩니다. 프록시 응답과 무관합니다. |
| `work_intel.analytics_enabled` | `WORK_INTEL_ANALYTICS_ENABLED` | `true` | 분석 API와 화면. 끄면 조회만 막고(503 `work_intel_analytics_disabled`) 분류와 집계는 계속됩니다. |
| `work_intel.interval` | `WORK_INTEL_INTERVAL` | `15s` | 워커 주기(1s~1h). |
| `work_intel.batch_size` | `WORK_INTEL_BATCH_SIZE` | `200` | 주기당 최대 처리 건수. 한 묶음은 한 트랜잭션입니다. |
| `work_intel.backfill_days` | `WORK_INTEL_BACKFILL_DAYS` | `7` | 처음 켤 때 과거 며칠 치부터 분류할지(0~365). 워커가 한 번 돈 뒤에는 바꿔도 시작 위치가 달라지지 않습니다. 과거 데이터는 재분류(6.5절)로 다시 처리합니다. |
| `work_intel.llm_enabled` | `WORK_INTEL_LLM_ENABLED` | `false` | 분류 모델 사용. 켜면 가린 프롬프트 일부와 카테고리 ID 목록이 분류 모델로 전송되고 호출 비용이 발생합니다. |
| `work_intel.llm_model` | `WORK_INTEL_LLM_MODEL` | (없음) | 분류에 쓸 모델. 운영 트래픽 모델과 분리해 작고 빠른 모델을 지정합니다. 비어 있으면 호출하지 않습니다. |
| `work_intel.llm_provider` | `WORK_INTEL_LLM_PROVIDER` | (없음) | 분류 모델을 호출할 Provider. 비우면 모델 이름으로 고릅니다. 기존 Provider 설정을 그대로 씁니다. |
| `work_intel.llm_allow_external` | `WORK_INTEL_LLM_ALLOW_EXTERNAL` | `false` | 외부 Provider로의 전송 허용. 꺼져 있으면 주소가 루프백·사설망·내부 도메인인 Provider로만 보냅니다. |
| `work_intel.llm_concurrency` | `WORK_INTEL_LLM_CONCURRENCY` | `2` | 분류 모델 동시 호출 수(1~16). |
| `work_intel.llm_max_per_minute` | `WORK_INTEL_LLM_MAX_PER_MINUTE` | `60` | 분당 호출 상한. 넘는 요청은 규칙 결과로 저장하고 다음 주기에 다시 시도합니다. |
| `work_intel.llm_timeout` | `WORK_INTEL_LLM_TIMEOUT` | `20s` | 호출 1회 제한 시간. |
| `work_intel.insight_enabled` | `WORK_INTEL_INSIGHT_ENABLED` | `true` | 트렌드·자동화 후보·인사이트를 만드는 주기 작업. |
| `work_intel.insight_interval` | `WORK_INTEL_INSIGHT_INTERVAL` | `6h` | 주기 작업 간격. 오래된 집계 정리도 이 간격으로 실행됩니다. |
| `work_intel.insight_llm_enabled` | `WORK_INTEL_INSIGHT_LLM_ENABLED` | `false` | 인사이트 문장을 모델로 다듬기. 집계 수치만 전달하고 프롬프트는 보내지 않습니다. 다듬은 문장의 숫자가 근거와 다르면 원래 문장을 씁니다. |
| `work_intel.retention_days` | `WORK_INTEL_RETENTION_DAYS` | `400` | 집계·세션·인사이트 보존 일수. 0이면 지우지 않습니다. 요청별 분류 결과는 요청 로그 보존 기간을 따라 함께 지워집니다. |

**분류 모델을 켜기 전에** 확인하세요.

- 가린(마스킹한) 프롬프트라도 그 일부가 분류 모델로 전송됩니다. 폐쇄망 운영이라면 내부 Provider의 모델을 지정하고 `llm_allow_external` 은 끈 상태로 둡니다.
- 분류 모델의 호출도 비용입니다. 분당 상한과 동시 호출 수가 그 예산입니다.
- 분류 모델이 응답하지 않거나 형식이 틀리면 규칙 결과가 그대로 쓰이고, 상태 탭의 실패 수가 늘어납니다. 요청 처리에는 영향이 없습니다.

## 4. 업무 분류 체계

기본 분류 체계는 대분류 12개와 그 아래 중분류로 구성됩니다.

| ID | 대분류 | 예 |
|---|---|---|
| `dev` | 소프트웨어 개발 | 코드 작성·수정, 디버깅, 코드 리뷰, 테스트, 설계 |
| `infra` | IT 인프라 운영 | 서버·컨테이너·네트워크·클라우드, 배포, 장애 대응 |
| `itsm` | IT 서비스 운영 | 요청·변경·문제 관리, 운영 문서 |
| `security` | 정보보호 | 취약점, 접근 통제, 보안 점검, 컴플라이언스 |
| `data` | 데이터 분석 | SQL, 통계, 시각화, 데이터 품질 |
| `office` | 일반 사무 | 문서·메일·회의록·번역·요약 |
| `planning` | 경영 및 기획 | 사업 계획, 시장 조사, 보고 |
| `support` | 고객 지원 | 문의 응대, 안내문 |
| `knowledge` | 지식 관리 | 위키, 온보딩, 검색·정리 |
| `ai` | AI 개발 | 프롬프트, RAG, 평가, 모델 운영 |
| `automation` | 업무 자동화 | 워크플로, 에이전트, 스크립트 |
| `other` | 기타 및 미분류 | 근거가 부족하거나 업무가 아닌 대화 |

업무 유형은 **언어·모델·클라이언트와 독립된 축**입니다. 같은 Go 코드를 다루더라도 디버깅은 `dev`, 배포 스크립트는 `infra`로 나뉠 수 있습니다.

분류 체계는 **업무 분류 관리**에서 조직에 맞게 바꿉니다(6절). 카테고리를 추가·수정·비활성·병합할 수 있고, 모든 변경은 버전으로 남습니다.

## 5. 업무 활용 분석 화면 읽기

화면 위쪽의 공통 필터(기간, 비교 기간, 팀, 업무 유형, 행위, 모델, 클라이언트, 지표)는 모든 탭에 적용되고 주소에 반영됩니다. 주소를 복사해 같은 조건의 화면을 공유할 수 있습니다.

**지표**는 세션 수, API 호출 수, 고유 사용자 수, 토큰, 비용, MCP 호출 수 가운데 고릅니다. 같은 화면도 지표를 바꾸면 순위가 달라집니다. 호출 수가 많은 업무와 비용이 큰 업무는 다를 수 있습니다.

| 탭 | 무엇을 보나 |
|---|---|
| **요약** | 핵심 지표와 이전 기간 대비 증감, 업무 유형 비중(도넛), 증감 추이(누적 영역), 조직×업무 히트맵, 신규·급증 업무, 인사이트 |
| **업무 유형** | 대분류 → 중분류 → 소분류로 내려가는 순위 막대와 트리맵, 팀 → 업무 → 모델 흐름(생키) |
| **조직** | 팀별 TOP 업무, 비중, 활성 사용자, 업무 다양성, 사용자당 세션, 비용, 늘어나는 업무, 다른 팀과의 편차, 확산 후보 |
| **모델** | 업무별 모델 점유율, 세션당 토큰·비용, 응답 시간 P50·P95, 오류·재시도·모델 전환 비율, 피드백, 더 싼 모델 후보 |
| **트렌드·자동화** | 7일·30일 급증, 신규, 특정 조직 집중, 확산, 감소, 비용 이상, 모델 의존 신호와 반복 업무 자동화 후보 |
| **세션·요청** | 세션 목록과 세션 상세(업무 구간, 모델 전환, 오류, DLP 적용 여부), 요청 목록 |
| **생산성** | 관측된 값(세션 수, 시간, 비용)과 추정값(절감 시간)을 나눠서 표시 |

숫자를 누르면 대분류 → 중분류 → 소분류 → 세션 → 요청 순으로 내려갑니다. 표는 서버에서 페이지를 나누고, CSV로 내보낼 수 있습니다(내보내기는 감사 기록에 남습니다).

### 해석할 때 주의할 점

- **미분류와 분류 실패는 숨기지 않습니다.** 합계에 포함되고 별도 행으로 보입니다. 미분류 비율이 높으면 수치를 그대로 믿기 전에 분류 관리의 검토 탭을 먼저 보세요.
- **세션은 명시된 것과 추론한 것을 구분합니다.** 클라이언트가 세션 ID를 보낸 경우와 게이트웨이가 시간 간격으로 묶은 경우가 다르게 표시됩니다.
- **API 성공은 업무 완료가 아닙니다.** 세션 상태는 `확인됨`(긍정 피드백 등 완료 근거가 있음), `오류로 끝남`, `알 수 없음`으로 나뉩니다. 근거가 없으면 `알 수 없음`입니다.
- **인당 지표의 분모는 활성 사용자입니다.** 조직의 인원수(정원)가 아니라 그 기간에 실제로 AI를 쓴 사용자 수입니다. 화면에도 그렇게 적혀 있습니다.
- **조직 분석은 성과 평가 지표가 아닙니다.** 사용량이 많다는 것은 일을 잘한다는 뜻도, 못한다는 뜻도 아닙니다. 어디에 지원과 확산이 필요한지 찾는 용도입니다.
- **표본이 적은 수치에는 표시가 붙습니다.** 요청이 30건 미만인 모델 비교에는 `표본 부족`이 붙고, 더 싼 모델 후보는 같은 업무에서 30세션 이상의 근거가 있고 오류율과 부정 피드백 비율이 나쁘지 않을 때만 제안합니다.
- **생산성 추정은 기준값이 있을 때만 나옵니다.** 관리자가 업무별 기준 소요 시간을 등록하고(분류 관리 → 기준값), 완료 근거가 있는 세션이 있어야 절감 시간을 추정합니다. 없으면 `추정 불가`와 그 이유가 보입니다. 숫자를 지어내지 않습니다.
- **자동화 후보는 추천일 뿐입니다.** 프롬프트 템플릿, Skill, MCP Tool, 워크플로, AI 에이전트, 배치 중 어떤 형태가 맞을지 제안하지만, 자동으로 등록하거나 실행하지 않습니다. 관리자가 검토 상태만 기록합니다.
- **인사이트 문장은 집계에 근거합니다.** 문장마다 기간, 비교 기간, 표본 수와 해당 화면으로 가는 링크가 붙습니다.

### 소그룹 보호와 사용자 식별자

프롬프트 원문 열람 권한(`super_admin`·`admin`·`security_admin`)이 없는 관리자에게는 다음이 적용됩니다.

- **소수 집단 보호**: 고유 사용자 수가 정책의 최소 그룹 크기(기본 3명, 분류 관리 → 정책에서 1~50명으로 조정)보다 적은 묶음은 세션·요청·사용자·토큰·비용·MCP 호출 **모든 수치**를 가리고 `보호됨`으로 표시합니다. 비중·증감처럼 거기서 나온 값도 가립니다.
- **뺄셈 방지**: 같은 표에서 하나만 가려져 있으면 합계에서 나머지를 빼서 알아낼 수 있으므로, 가장 작은 다른 항목을 함께 가립니다. 그래서 `보호됨` 항목이 실제보다 많아 보일 수 있습니다. 가린 항목은 크기 순서가 드러나지 않게 맨 뒤에 둡니다. 합계 옆에 `(일부 보호됨)`이 붙으면 보이는 항목만 더한 값입니다.
- **추이·흐름**: 작은 업무는 추이에서 따로 선을 그리지 않고 `기타`에 들어가며, 흐름(생키)에서는 작은 팀·업무·모델이 열마다 `기타`로 묶입니다. 하루 단위 추이는 날마다 인원이 적어 가려지는 점이 많으니, 주 단위로 보거나 기간을 넓히세요.
- **범위 전체가 작을 때**(예: 사용자가 2명인 팀으로 거른 경우): 어떤 업무·모델을 썼는지도 드러나지 않도록 세부 항목 없이 "이 범위는 참여 사용자가 적어 세부 항목을 보여 주지 않습니다"가 표시됩니다.
- **분류 품질 분포**(요약 탭의 신뢰도·분류 방식·상태 분포)는 보이지 않습니다. 분류 관리 담당자용 정보이기 때문입니다.
- **신호·인사이트·자동화 후보**: 해당 인원이 최소 그룹 크기보다 적은 항목은 보이지 않습니다.
- **사용자 식별자**는 가명(`사용자-xxxxxxxxxx`)으로 보입니다. 같은 사용자는 항상 같은 가명입니다. 게이트웨이 비밀값(`GATEWAY_SECRET`)과 JWT 비밀값이 모두 기본값이면 가명을 만들 안전한 키가 없으므로 사용자 칸을 비웁니다.
- **프롬프트에서 뽑은 텍스트**(업무 제목·태그·기술, 새 카테고리 후보 문구)는 보이지 않고, 업무 제목 자리에는 카테고리 이름이 나옵니다.
- 팀 관리자는 **자기 팀의 데이터만** 봅니다. 집계, 목록, 세션 상세, 검토, 보정, 내보내기 모두 같습니다. 다른 팀과 함께 걸린 자동화 후보의 검토 상태는 바꿀 수 없습니다.

소수 집단 보호는 **집계 화면이 몇 사람의 업무 내역을 드러내지 않도록 하는 장치**이지, 새 접근 경계가 아닙니다. 한 화면(한 번의 응답)에서, 또는 같은 화면을 두 번 조회한 값을 빼서 소수 집단의 숫자를 바로 읽을 수 없게 합니다. 하지만 여러 화면과 필터의 숫자를 모아 연립해서 푸는 것까지 막지는 않습니다. 위 역할들은 기존 요청 탐색기에서 개별 요청(가린 프롬프트 포함)을 이미 열 수 있고, 세션·요청 목록도 같은 범위에서 보이기 때문입니다. 개별 요청 열람 자체를 막으려면 해당 관리자의 역할 권한을 조정하세요.

## 6. 업무 분류 관리

`/app/insights/classification`. 조회는 `admin:read`, 변경은 `admin:write` 권한이 필요하고 모든 변경은 감사 기록에 남습니다. 테스트와 평가도 `admin:write`가 필요합니다.

팀 범위 관리자는 자기 팀의 검토·보정·재분류만 할 수 있습니다. 조직 전체에 영향을 주는 정책 저장·배포·되돌리기, 재집계, 인사이트 다시 만들기는 전체 관리자만 할 수 있습니다.

### 6.1 상태

워커가 돌고 있는지, 미처리가 얼마나 쌓였는지, 분류 방식별 처리 건수, 분류 모델 호출과 실패, 적용 중인 정책 버전을 봅니다. 분류 모델이 꺼져 있거나 허용되지 않은 Provider라서 호출하지 않는 경우 그 이유가 여기에 나옵니다.

### 6.2 카테고리와 규칙

카테고리 트리에서 이름, 설명, 상위 카테고리, 규칙(핵심어·도구 이름·API 종류·클라이언트·언어와 가중치)을 고칩니다.

- **비활성**: 새 요청이 그 카테고리로 분류되지 않습니다. 과거 데이터는 상위 카테고리로 접어서 보여 줍니다.
- **병합**: 카테고리 A를 B로 합치면 A로 분류된 과거 데이터가 B로 보입니다. 원본은 바뀌지 않으므로 되돌릴 수 있습니다.
- 편집은 **초안**에만 저장됩니다. 배포하기 전에는 분류에 영향을 주지 않습니다.
- 두 사람이 동시에 고치면 나중에 저장한 쪽이 충돌 안내를 받습니다(덮어쓰지 않습니다).

### 6.3 정책·버전

초안을 **배포**하면 새 버전이 됩니다. 배포 전에 무엇이 바뀌는지(추가·수정·비활성·병합된 카테고리)와 영향받는 과거 요청 수를 보여 줍니다. 이전 버전으로 **되돌리기**는 그 버전의 내용을 새 버전으로 다시 배포합니다(이력은 지워지지 않습니다). 되돌리기는 초안도 그 버전 내용으로 바꾸므로, 다른 관리자가 저장만 하고 배포하지 않은 초안 수정은 사라집니다. 되돌리기 전에 정책·버전 탭에 `초안이 배포본과 다름` 표시가 있는지 확인하세요.

배포는 **이후에 들어오는 요청**부터 적용됩니다. 이미 분류된 요청을 새 정책으로 다시 분류하려면 재분류(6.5절)를 실행합니다.

### 6.4 테스트와 검토

- **테스트**: 문장을 넣어 초안 또는 배포된 정책으로 어떻게 분류되는지, 어떤 근거로 점수가 났는지 봅니다. 입력한 문장은 저장되지 않습니다. 관리자가 보정한 요청으로 정책의 정확도를 다시 재 보는 평가도 여기서 실행합니다(보정이 20건 미만이면 평가하지 않습니다).
- **검토**: 미분류, 신뢰도가 낮은 요청, 분류 실패, 새 카테고리 후보를 모아 봅니다. 요청을 골라 올바른 카테고리로 **보정**하면 집계가 즉시 다시 계산됩니다. 한 번에 500건까지 고칠 수 있습니다.
- 보정은 **검증 데이터**로 쌓입니다. 보정이 정책을 자동으로 바꾸지는 않습니다. 같은 보정이 반복되면 규칙을 고쳐 배포하세요.
- 수동으로 보정한 요청은 이후 재분류에서도 유지됩니다.

### 6.5 재분류와 재집계

- **재분류**: 기간과 조건을 정하면 먼저 영향받는 건수(상태별·방식별, 유지되는 수동 보정 수, 예상 분류 모델 호출 수)를 보여 줍니다. 확인한 뒤 실행하면 백그라운드 작업으로 돌고 진행률이 표시됩니다. 미리보기는 5분 동안 유효하고, 그 사이 대상이 바뀌면 다시 확인해야 합니다. 작업은 한 번에 하나만 실행됩니다. 미리보기 뒤 워커가 그사이 다시 처리한 요청(분류 모델 재시도 등)은 이번 작업에서 빠지고, 진행 화면에 미리보기 때 건수와 함께 표시됩니다. 정책 버전이나 선택 조건이 바뀌었으면 다시 미리보기 해야 합니다. 작업 도중 인스턴스가 재시작되면 작업은 `중단됨`으로 끝나고, 그때까지 처리한 요청은 반영된 채로 남습니다. 자동으로 이어서 하지는 않으므로 다시 미리보기 하고 실행하세요(이미 처리한 요청도 다시 대상이 되지만 결과는 같습니다).
- **프롬프트 보존 기간이 지난 요청**: 가린 텍스트가 이미 지워진 요청은 재분류해도 기존 분류를 그대로 둡니다(근거 없이 미분류로 떨어뜨리지 않기 위해서입니다). 원래 미분류·실패였던 요청만 메타데이터 규칙으로 다시 보고, 분류 모델에는 보내지 않습니다. 미리보기와 진행률에 `텍스트 없음으로 유지` 건수가 따로 나옵니다.
- **재집계**: 분류 결과는 그대로 두고 일별 집계만 다시 만듭니다(한 번에 최대 92일). 집계가 어긋났다고 의심될 때 씁니다.

두 작업 모두 묶음 단위로 쉬어 가며 실행해 DB를 독점하지 않습니다.

### 6.6 기준값

업무별 기준 소요 시간(사람이 직접 할 때 걸리는 시간)을 등록합니다. 생산성 탭의 절감 시간 추정에만 쓰입니다. 등록하지 않은 업무는 추정하지 않습니다.

## 7. 개인정보와 보안

- **원문 프롬프트를 저장하도록 강제하지 않습니다.** 분류는 이미 저장된 가린(마스킹한) 텍스트만 읽습니다. 가린 텍스트가 없으면 메타데이터로만 분류합니다.
- 분류 결과에 붙는 업무 제목과 태그는 저장 전에 다시 한 번 가립니다(비밀값·개인정보 패턴).
- 분류 모델 전송은 **기본 꺼짐**이고, 켜도 내부 Provider로만 보냅니다. 외부 전송은 별도 설정을 켜야 합니다.
- 인사이트를 모델로 다듬을 때는 집계 수치만 보냅니다.
- 테스트 탭에 넣은 문장은 저장하지도 기록하지도 않습니다.
- 팀 범위, 소그룹 보호, 가명 처리는 화면만이 아니라 API와 CSV 내보내기에도 똑같이 적용됩니다.
- 보존: 요청별 분류 결과는 요청 로그와 함께 지워지고, 집계·세션·인사이트는 `work_intel.retention_days`를 따릅니다.

## 8. 운영

### 8.1 관측 (`/metrics`)

| 메트릭 | 뜻 |
|---|---|
| `proxy_work_intel_processed_total{method}` | 분류한 요청 수(방식별: 규칙·캐시·모델 등) |
| `proxy_work_intel_backlog` | 분류를 기다리는 요청 수(상한까지만 셉니다) |
| `proxy_work_intel_lag_seconds` | 가장 오래 기다린 요청의 대기 시간 |
| `proxy_work_intel_batch_seconds` | 묶음 하나를 분류하고 반영하는 데 걸린 시간(합계·횟수) |
| `proxy_work_intel_llm_calls_total` | 분류 모델 호출 수 |
| `proxy_work_intel_cache_hits_total` | 캐시로 분류한 요청 수 |
| `proxy_work_intel_failures_total` | 분류 모델 호출 실패와 워커 주기 실패 |

카운터는 임대를 잡고 실제로 분류하는 인스턴스에서만 올라갑니다. 여러 인스턴스를 띄웠다면 합산해서 보세요.

### 8.2 점검 기준

- `proxy_work_intel_lag_seconds` 가 계속 늘면 유입이 처리량보다 많은 것입니다. `work_intel.batch_size` 를 키우거나 `work_intel.interval` 을 줄입니다.
- `proxy_work_intel_failures_total` 이 늘면 상태 탭에서 사유를 확인합니다. 대부분 분류 모델의 시간 초과나 형식 오류입니다.
- 규칙만 쓸 때 묶음 200건의 처리 시간은 개발 장비 기준 SQLite 약 14ms, PostgreSQL 약 35ms입니다.

### 8.3 끄기와 되돌리기

- **분석 화면만 끄기**: `work_intel.analytics_enabled=false`. 분류와 집계는 계속됩니다.
- **분류만 끄기**: `work_intel.classify_enabled=false`. 화면은 이미 쌓인 데이터를 계속 보여 줍니다. 다시 켜면 멈춘 지점부터 이어집니다.
- **이전 버전으로 내리기**: 추가된 테이블은 이전 버전이 읽지 않으므로 그대로 두어도 됩니다. 꼭 지워야 한다면 아래 14개만 삭제합니다. `work_apps` 는 이 기능의 테이블이 아니므로(업무 앱) 지우면 안 됩니다.
  `work_intel_policy`, `work_intel_policy_versions`, `work_intel_state`, `work_intel_jobs`, `work_intel_dirty`, `work_classifications`, `work_class_cache`, `work_corrections`, `work_sessions`, `work_session_segments`, `work_daily`, `work_daily_users`, `work_automation_candidates`, `work_insights`

## 9. 알려진 한계

- **규칙만으로는 정확도에 한계가 있습니다.** 직접 라벨을 붙인 346개 문장에서 대분류 정확도는 전체 92.5%였고, 규칙을 만들 때 보지 않은 검증 묶음에서는 83.3%였습니다. 확정으로 받아들인 결과만 보면 94~98%입니다. 같은 문장 묶음으로 만든 요청 6,142건을 실제 게이트웨이(PostgreSQL)에 흘려 워커로 분류했을 때는 대분류 89.4%, 확정 결과 정밀도 94.3%, 미분류 1.0%였습니다(규칙을 다듬을 때 본 문장이 섞여 있어 독립 검증 수치는 아닙니다). 조직의 실제 데이터에서는 다를 수 있으니 검토 탭의 보정과 평가로 확인하세요.
- **SQLite에서는 큰 재집계가 요청 처리를 잠깐 멈출 수 있습니다.** SQLite 저장소는 연결 하나를 공유하므로, 보정·재분류 뒤의 날짜별 재집계나 주기 작업(자동화 후보 계산)이 도는 동안 같은 DB를 쓰는 요청 처리가 기다립니다. 하루 6만 건 규모에서 하루치 재집계가 약 0.2초, 후보 계산이 약 0.07초 동안 막는 것을 측정했습니다. 평소의 분류 묶음(200건)은 십수 ms 걸립니다. 요청이 많은 운영 환경은 PostgreSQL을 쓰세요. PostgreSQL은 연결을 여러 개 쓰므로 재집계가 요청 처리의 DB 조회를 막지 않습니다.
- **소수 집단 보호에는 비용이 듭니다.** 원문 열람 권한이 없는 관리자에게는 가릴 칸을 정하려고 고유 사용자 수를 더 셉니다. 요청 분류 5만 건 규모에서 흐름·추이 화면은 수 ms에서 약 90ms로, 60일 모델 화면은 PostgreSQL에서 약 55ms에서 270ms로 늘었습니다. 기간 상한(400일) 안에서 분류 건수에 비례합니다.
- **재분류 작업은 재시작 뒤 이어서 하지 않습니다**(6.5절). 처리한 부분까지만 반영되고 `중단됨`으로 끝납니다.
- **집계 보존 일수는 요청 로그 보존 일수보다 길게 두세요.** `work_intel.retention_days`가 더 짧으면 집계가 먼저 지워지고 요청별 분류는 남아, 나중에 그 날짜를 재집계할 때 일부 날짜만 다시 생깁니다.
- **여러 인스턴스가 인사이트를 동시에 만들면** 드물게 두 번의 생성 결과가 섞일 수 있습니다. 다음 주기에 다시 만들어집니다.
- **임베딩 유사도 분류는 없습니다.** 같은 내용(지문)이 다시 올 때의 캐시만 있습니다.
- **부서 계층과 정원 정보가 없습니다.** 조직 축은 팀 하나이고, 인당 지표의 분모는 활성 사용자입니다.
- **세션 안의 업무 구간은 카테고리·날짜 단위로 나눕니다.** 시간 순서대로 목적이 바뀐 지점을 정밀하게 자르지는 않습니다.
- **수집 시각이 없는 아주 오래된 요청은 분류하지 않습니다.**
- **완료 여부는 근거가 있을 때만 판단합니다.** 피드백이 없는 대부분의 세션은 `알 수 없음`입니다.
